# gartha.me — Personal site, blog, and admin

Date: 2026-09-07
Status: approved design, ready for planning

## Goal

A personal website at gartha.me with a public blog and a private admin
area. The admin shows a daily report generated by a scheduled job. The
first version runs entirely on Cloudflare's free tier. The only paid
items are the domain (already owned) and, later, xAI API usage for the
daily report.

Design direction is settled: a playful game "character select" look
with a programmer identity. Mockups live at
https://claude.ai/code/artifact/9d5a6b5a-c93c-4cf6-8d60-ee54e2e165f0
and the source artboards are in `design/*.dc.html`.

## Scope of this spec

In scope:

- Public site: home, blog list, blog post.
- Admin: daily report view, "run now" trigger, report history by date.
- Scheduled job that produces a daily report and stores it.
- Monorepo, tooling, deploy pipeline.

Deferred to later specs:

- Email ingestion and Grok curation. The job in this version writes a
  report with a stub summary so the pipeline and UI can be built and
  tested end to end. The email source and the Grok prompt are a
  separate piece of work.
- Admin "Posts", "Inbox rules", and "Settings" pages. They appear in
  the admin sidebar mockup as disabled links.
- Projects page. It appears in the nav mockup as a disabled link.
- Search on the blog list.

## Architecture

One Cloudflare Worker serves everything at gartha.me.

```
Browser
  │
  ▼
Cloudflare Worker (apps/api, Hono)
  ├─ /api/*            JSON API (Hono routes)
  ├─ /admin/*, /api/admin/*   behind Cloudflare Access
  ├─ everything else   static assets from apps/web/dist
  └─ scheduled()       daily cron → writes a report to D1
  │
  ▼
D1 (SQLite)  reports, job_runs
```

- The Astro app builds to static HTML. It never runs on the server.
- The Worker's assets binding serves the Astro output. Unmatched
  routes fall through to assets, so Astro's own 404 page works.
- The admin page is static HTML plus a small client script that calls
  `/api/admin/*`. Cloudflare Access gates both the page and the API.
- The cron handler and the "run now" endpoint call the same function.

### Why not the Astro Cloudflare adapter

The adapter makes Astro itself the Worker. That works for server-rendered
pages but gives no clean home for a cron handler and ties the backend to
Astro's build. Keeping Astro static and putting Hono in front keeps the
two sides independently replaceable.

## Components

### apps/web (Astro)

Pages, all static:

- `/` Home. Character hero, badge, level bar, intro copy, two CTAs,
  main stack card, stats card, latest post strip. Stats and level are
  values in a single `src/data/profile.ts` file so they are easy to
  edit without touching markup.
- `/blog` Blog list. Featured post (most recent, or `featured: true`
  in frontmatter), grid of remaining posts, category filter chips.
  Filtering is client-side over the already-rendered cards, no API.
  Pagination at 12 posts per page.
- `/blog/[slug]` Post. Header card, body rendered from Markdown with
  Shiki code highlighting in the dark terminal style, previous and
  next links in date order.
- `/admin` Admin shell. Static layout with sidebar. On load, fetches
  `/api/admin/reports/latest` and renders it. Date picker calls
  `/api/admin/reports/:date`. "Run now" posts to
  `/api/admin/reports/run` and then reloads the latest report.

Content collection schema for blog posts:

```ts
{
  title: string
  description: string
  date: Date
  category: 'code' | 'games' | 'builds'
  featured?: boolean
  draft?: boolean
}
```

Read time is computed at build time from word count at 200 wpm.
Drafts are excluded from production builds.

### packages/ui

Astro components that reproduce the mockups. No client JS.

- `Character.astro` The SVG character. Props: `variant`
  (`'coder' | 'gamer' | 'builder'`, controls hoodie color and held
  item), `size`. Also an `Avatar.astro` face-only crop for bylines.
- `Badge.astro` Angled label (PLAYABLE, FEATURED).
- `StatRow.astro` Icon tile plus label and value.
- `Card.astro` White rounded card with the hard offset shadow, optional
  floating title pill.
- `Button.astro` Primary (blue) and secondary (white) with offset shadow.
- `CategoryChip.astro` Mono tag colored by category.
- `tokens.css` Palette, type scale, radii, shadow. Fonts: Baloo 2 for
  display, Nunito for body, JetBrains Mono for code and labels, loaded
  from Google Fonts with system fallbacks.

### apps/api (Hono on Workers)

Routes:

| Method | Path                          | Purpose                                  |
| ------ | ----------------------------- | ---------------------------------------- |
| GET    | /api/health                   | liveness, returns version and time       |
| GET    | /api/admin/reports/latest     | most recent report                       |
| GET    | /api/admin/reports/:date      | report for a YYYY-MM-DD date             |
| GET    | /api/admin/reports            | list of dates that have a report         |
| POST   | /api/admin/reports/run        | run the daily job now, return the report |

Everything under `/api/admin` checks the `Cf-Access-Jwt-Assertion`
header and validates the JWT against the Access team's public keys.
Requests without a valid token get 401. This is defense in depth
behind the Access rule.

`scheduled()` runs at 22:00 UTC daily (07:00 in UTC+9; adjust the cron
string if the timezone differs) and calls `runDailyReport`.

Bindings in `wrangler.toml`: `ASSETS` (apps/web/dist), `DB` (D1),
secrets `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD`.

### Daily report job

`runDailyReport(db, now)`:

1. Insert a `job_runs` row with status `running`.
2. Produce a `Report`. In this version the producer is a stub that
   returns fixed counts and a summary saying the source is not yet
   connected. The producer is an interface so the email and Grok
   version slots in later.
3. Upsert the report for `now`'s date.
4. Mark the run `ok` or `failed` with the error message.

Running twice on the same date replaces that date's report. The run
history is kept for the cron log panel.

### packages/db (Drizzle + D1)

```sql
reports (
  date        TEXT PRIMARY KEY,   -- YYYY-MM-DD
  generated_at TEXT NOT NULL,
  emails_read INTEGER NOT NULL,
  needs_reply INTEGER NOT NULL,
  bills_due   INTEGER NOT NULL,
  archived    INTEGER NOT NULL,
  summary     TEXT NOT NULL,
  items       TEXT NOT NULL       -- JSON array of {kind, title, note, priority}
)

job_runs (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  started_at  TEXT NOT NULL,
  finished_at TEXT,
  status      TEXT NOT NULL,      -- running | ok | failed
  error       TEXT,
  trigger     TEXT NOT NULL       -- cron | manual
)
```

Migrations are plain SQL files applied with `wrangler d1 migrations`.
Drizzle is used for typed queries only.

## Data flow

- Build: Turborepo builds `packages/ui`, then `apps/web` (static
  output), then `apps/api` (Wrangler bundles the Worker with the assets
  directory).
- Request for a page: Worker → assets binding → HTML.
- Admin load: static page → client fetch → Hono → D1 → JSON → DOM.
- Cron: Cloudflare → `scheduled()` → `runDailyReport` → D1.

## Error handling

- API returns JSON errors `{ error: string }` with proper status codes.
  404 for a missing report date, 401 for missing or invalid Access
  token, 500 with a generic message for unexpected failures. Details
  go to Worker logs, not the response.
- Admin page shows an inline error card when a fetch fails, and keeps
  the last good report on screen.
- Job failures are recorded in `job_runs` and surface in the cron log
  panel. A failed run does not overwrite the previous day's report.
- Build fails on invalid frontmatter thanks to the content schema.

## Testing

- `packages/db`: migration applies cleanly against a fresh local D1.
- `apps/api`: Vitest with `@cloudflare/vitest-pool-workers`. Tests for
  each route, the Access JWT check (valid, missing, expired), and the
  job (writes a report, records a failed run when the producer throws,
  replaces a same-day report).
- `apps/web`: build succeeds with the sample posts; a smoke test that
  the three pages and the admin shell render expected landmarks.
- `packages/ui`: rendered-output snapshot for `Character.astro` per
  variant.
- CI on GitHub Actions: lint, typecheck, test, build on every PR.

## Deployment

- Local: `pnpm dev` runs Astro dev and `wrangler dev` side by side.
  Wrangler serves the API and a local D1.
- Production: Cloudflare Workers Builds watches `main`, runs
  `pnpm build`, then `wrangler deploy`. D1 migrations run as a build
  step.
- Custom domain: the Worker is bound to gartha.me and www.gartha.me
  with a redirect from www to apex.
- Cloudflare Access application covers `gartha.me/admin*` and
  `gartha.me/api/admin*`, policy allows garthaprasidhiyanta@gmail.com
  via Google or one-time PIN.
